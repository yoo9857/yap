# 물 시스템 차세대 설계 (곡선 파도 · 심해)

작성 2026-11-11. 상태: **A·B 단계 구현됨**(같은 날, `render/waterPipeline.ts`, 마우스가 있는 기기에서 기본 켜짐 —
`docs/WATER.md` 마지막 절). 나머지 단계는 아래 "결정이 필요한 것"이 정해진 뒤에 한다.
현재 구현의 사실 관계는 `docs/WATER.md`가 기준이다.

## 1. 왜 다시 설계하는가

지금 물은 한 종류다: 1 m 칸에 든 물(마인크래프트식)을 표면 메시로 감싸 한 번에 그린다.
이 구조로는 다음이 원리적으로 안 된다.

| 원하는 것 | 지금 안 되는 이유 |
|---|---|
| 곡선 파도 | 수면 높이가 칸마다 고정값(가득 0.875, 흐르는 물 0.10‒0.56)이다. 파도는 연속 함수여야 한다. |
| 심해 | 세계 높이가 56칸이다(`WORLD_Y`). 수백 m 깊이를 칸으로 채울 수 없고, 채워도 30만 칸 저장 한도를 넘는다. |
| 물속에서 물밖이 제대로 보임 | 장면을 한 번에 그려서 물이 "뒤에 뭐가 있는지, 물이 얼마나 두꺼운지" 모른다. 안개도 화면 전체 단위다. |
| 물막 안쪽이 빈 공간으로 보임 | 같은 이유. 물 두께를 픽셀마다 알아야 한다. |

그래서 설계의 축은 두 개다: **물을 두 종류로 나눈다**, **렌더링을 깊이를 읽는 방식으로 바꾼다**.

## 2. 목표와 비목표

목표
- 바다: 끝없이 이어지는 수면, 곡선 파도, 수심에 따라 어두워지는 심해.
- 지은 물(양동이·샘): 지금처럼 블록 세계의 일부. 유한한 양(`fluidVolume.ts`)으로 간다.
- 물 위·물속·수면에 걸친 화면이 픽셀 단위로 맞는다.
- 웹, 안드로이드 앱(wgpu), 교실 서버가 같은 규칙을 쓴다(기존 Rust 코어 원칙 유지).
- 저사양 휴대폰에서도 돈다: 품질 단계를 두고 최저 단계는 지금 수준의 비용.

비목표 (이번 설계에서 하지 않는 것)
- 물리 기반 유체(입자·격자 Navier–Stokes). 파도가 블록을 밀거나 해안에 부서져 쌓이는 것.
- 배·잠수함 같은 탈것, 해양 생물. (설계는 이들을 막지 않게만 한다.)
- 기존 저장 형식 변경. 블록 번호 19‒28은 그대로다.

## 3. 물의 두 종류

### 3.1 바다 (새로 만드는 것)

- **칸이 아니다.** 해수면 높이 `SEA_Y`와 파도 함수 `wave(x, z, t)`로 정의되는 연속 수면이다.
  저장할 것이 없다(시드 + 시간).
- **파도 함수는 하나, 세 군데서 쓴다.** 셰이더(그리기), 클라이언트 CPU(부력·카메라·소리),
  서버(필요해지면 판정). 그래서 함수는 "결정적이고 싸야" 한다.
  1단계는 **Gerstner 파 4‒6개의 합**(곡선 마루, 뾰족한 파봉 표현 가능, CPU에서 한 점 계산이
  수백 ns). 2단계에서 필요하면 FFT 스펙트럼 텍스처를 셰이더에만 더한다(CPU는 Gerstner 유지:
  잔물결은 물리에 영향을 주지 않게 한다).
- **패리티 규칙을 그대로 따른다**: `packages/shared/src/ocean.ts`(기준) ↔
  `engine/crates/core/src/ocean.rs`, 같은 입력에 같은 float 결과를 요구하는 테스트.
  셰이더 쪽은 같은 상수 표를 유니폼으로 받는다(상수는 한 곳에서 생성).
- **수면 메시**: 카메라를 따라오는 동심 격자(클립맵) — 가까이는 0.5 m, 멀리 갈수록 2배씩
  성긴 링. 정점은 셰이더에서 파도 함수로 변위한다. 정점 수는 고정(약 2만‒6만, 품질 단계별).
- **해안**: 수심이 얕아지면 파고를 줄인다(`amplitude × smoothstep(0, 4 m, 수심)`). 수심은
  지형 높이맵에서 읽는다(섬: `generateIsland`의 높이; 들판: 바다 없음이 기본).
- **블록과의 경계**: 바다는 지형 블록에 가려진다(깊이 테스트). 해수면보다 낮고 바다와
  이어진 빈 칸은 "바닷물이 찬 것"으로 취급한다 — 칸에 물을 써 넣지 않고, 질의 함수
  `seaAt(x, y, z)`가 답한다. 연결 여부는 구역 단위 flood fill을 캐시한다(블록 편집 시 그
  구역만 무효화). 이렇게 해야 바닷가에 구덩이를 파면 물이 차고, 저장 칸 수는 늘지 않는다.

### 3.2 지은 물 (지금 것의 연장)

- 규칙은 **유한한 물**(`fluidVolume.ts`)로 간다: 같은 번호를 양으로 읽고, 양동이는 물 한
  칸, 예전에 부은 물(19)은 샘. 남은 일은 `docs/WATER.md` 마지막 절의 순서 그대로다
  (샘 아이템 → Rust 쌍둥이 → 교실 서버 → 섬 → 모양 블록 → E2E).
- 표면 메시(`waterGeometry.ts` ↔ `water_mesh.rs`)는 유지한다. 오늘까지 넣은 물막·필름·
  모서리 이음이 그대로 쓰인다.
- 바다와 만나는 곳: 지은 물의 칸이 `seaAt`인 칸과 닿으면 그 칸은 바다에 흡수된다(양이
  사라짐 = 바다로 흘러 들어감). 반대로 바다가 지은 수조로 넘어 들어오지는 않는다(수조
  벽이 해수면보다 낮으면 그 칸들은 처음부터 `seaAt`).

### 3.3 심해

- 세계 높이를 늘리지 않는다. **심해는 섬 바깥의 바다 영역**이다: 지형 블록 격자(160×160)는
  섬과 대륙붕까지만, 그 밖은 해저 높이맵(절차 생성, 칸 아님)과 바다 수면이다.
- 해저는 낮은 해상도 메시(수면과 같은 클립맵, 높이맵 변위)로 그린다. 블록이 아니므로 캘 수
  없다 — "심해에서 건축"이 필요하면 별도 결정(§9).
- **깊이대**: 햇빛대(0‒30 m) → 박명대(30‒120 m) → 암흑대(120 m‒). 깊이에 따라 (a) 빛 색이
  빨강부터 사라지고(파장별 흡수), (b) 가시거리가 줄고, (c) 주변광이 0에 가까워진다.
  암흑대에서는 손전등/발광 블록만 보인다. 이것은 전부 §4의 물속 패스의 매개변수다.

## 4. 렌더링 파이프라인

지금: 장면을 캔버스에 한 번에 그린다(잉크 패스는 기본 꺼짐).
바꿀 것: **불투명 장면을 먼저 색+깊이 텍스처로 그리고, 물은 그것을 읽으며 그린다.**

```
1  그림자 패스                      (그대로)
2  불투명 장면  →  sceneColor, sceneDepth      (렌더 타깃; 톤매핑 전 선형색)
3  물 패스 (바다 수면 + 지은 물 메시)  →  같은 타깃에 합성, waterMask/waterDepth 기록
4  물속 패스 (전체 화면 1회)         →  수면 아래 픽셀만: 경로 길이 안개, 색 흡수, 빛줄기
5  톤매핑 + 출력                    (지금 잉크 합성이 하는 일과 같은 자리)
```

물 패스에서 깊이를 읽어 얻는 것 (전부 한 셰이더, 추가 패스 없음)
- **두께**: `sceneDepth − 물 표면 깊이` = 물을 통과한 거리. Beer–Lambert 흡수로 색과
  불투명도를 정한다. 얕은 물은 맑고 깊은 물은 짙다. 지금의 정점 속성 `aDepth`(칸 수 기반
  추정)를 대체한다.
- **굴절**: 법선으로 화면 좌표를 조금 밀어 `sceneColor`를 읽는다. 민 자리가 물 앞의
  물체면 밀지 않는다(깊이 비교) — 물 위 물체가 물에 번지는 흔한 결함을 막는다.
- **부드러운 물가**: 두께가 0에 가까우면 투명해진다. 블록과 만나는 딱딱한 선이 사라진다.
- **거품**: 두께가 얇은 곳(해안선·물체 주변) + 파봉(Gerstner 야코비안) + 낙수 지점(지금의
  `aImpact`).
- **반사**: 1단계는 지금의 하늘 환경맵(`skyEnvironment.ts`) + 프레넬. 2단계 선택 사항으로
  화면 공간 반사(SSR, 고품질 단계만).

물속 패스 (수면 아래 픽셀에만 적용)
- **어느 픽셀이 물속인가**: 카메라가 물속이면 "물 표면 뒷면이 그려지지 않은 픽셀 전부 +
  뒷면까지의 구간"이 물속이다. 3번 패스에서 물 표면의 앞/뒷면 깊이를 `waterDepth`에 적어
  두고 4번이 읽는다. 그러면 **수면에 걸친 화면이 픽셀 단위로 갈리고**, 물막으로 둘러싸인
  공기 공간은 공기로, 물막 자체는 물로 보인다(오늘 DOM 덮개로 흉내 낸 것의 정식 구현).
- **경로 길이 안개**: 픽셀마다 `물속을 지난 거리`로 흐리게 한다. 지금의 전역 안개(12 m)를
  대체한다. 색은 깊이대(§3.3)에서 온다.
- **빛줄기·코스틱**: 고품질 단계만. 코스틱은 타일링 텍스처 2장을 흘려 물속 바닥에 곱한다
  (진짜 계산 아님, 값이 쌈).

기존 규칙과의 관계 (CLAUDE.md의 load-bearing 항목)
- 렌더 타깃에 그리면 three가 톤매핑을 건너뛴다 → 5번에서 직접 한다. 잉크 패스가 이미 같은
  일을 하고 있으니 그 합성 셰이더를 일반화한다.
- "한 프레임에 한 재질이 두 셰이더 변형을 쓰지 않는다": 물 재질은 패스별 인스턴스로
  나누고 프로그램은 공유한다(오늘 넣은 `uPass` 방식).
- WebXR(빌더 VR)은 프레임버퍼를 헤드셋이 소유한다 → VR에서는 이 파이프라인을 끄고 지금
  방식으로 떨어진다(빌더 모드에는 물이 없어 영향 없음).
- 오늘 넣은 3패스(수평면 → 깊이 → 가파른 면)는 이 파이프라인이 들어오면 필요 없어진다
  (두께를 직접 아니까). 최저 품질 단계의 대체 경로로만 남긴다.

## 5. 품질 단계와 비용 예산

측정값이 아니라 **목표**다. 각 단계는 구현 시 `tools/perf-craft.mjs`로 실측해 맞춘다.

| 단계 | 대상 | 내용 | 물 관련 추가 비용 목표 |
|---|---|---|---|
| 낮음 | 저사양 휴대폰 | 지금 방식(렌더 타깃 없음) + 바다는 평평한 수면에 법선 텍스처만 | 지금과 같음 |
| 보통 | 일반 휴대폰·노트북 | 색+깊이 타깃(해상도 0.75배), 두께·부드러운 물가, Gerstner 변위 | 프레임당 +2 ms 이내 |
| 높음 | PC | 전체 해상도, 굴절, 물속 패스, 코스틱, 빛줄기 | 프레임당 +4 ms 이내 |

- 기본값은 지금의 `auto` 그래픽 설정에 묶는다. 설정에서 바꿀 수 있다.
- 깊이 텍스처를 못 쓰는 기기(드묾, WebGL2 필수 기능이지만 드라이버 문제 대비)는 "낮음"으로.

## 6. 플랫폼

- **웹**: three.js/WebGL2. 위 파이프라인을 `GameRenderer`에 넣는다(모든 모드가 공유하므로
  물이 없는 모드에서는 2번 타깃을 만들지 않는다).
- **안드로이드(wgpu)**: 렌더 패스 구조는 같다. 셰이더는 WGSL로 다시 쓴다(자동 변환하지
  않는다: 지금도 앱 렌더러는 별도 구현). 파도 상수 표와 `ocean.rs`를 공유한다.
- **서버**: 바다는 서버가 계산하지 않는다(상태가 없음). `seaAt` 판정이 서버 규칙에
  필요해지는 곳은 블록 놓기 검증과 지은 물의 흡수뿐이다 → `ocean.rs`의 해수면 상수와
  flood fill을 Rust 코어에 둔다.
- **교실**: 프로토콜에 추가되는 것은 "이 세계에 바다가 있는가 + 시드" 정도다(환영 메시지의
  선택 필드, 버전 올림 1회). 파도 위상은 이미 있는 서버 시계 `ts`에서 얻어 모두 같은 파도를
  본다.

## 7. 단계별 계획과 통과 기준

각 단계는 혼자서 배포 가능한 크기이고, 플래그 뒤에서 시작한다(`?water2=1`).

| 단계 | 내용 | 통과 기준 |
|---|---|---|
| A | 색+깊이 타깃, 물 패스가 두께를 읽음(흡수·부드러운 물가). 지은 물만. | `shot-water-flow`의 모든 장면에서 물가 경계선이 사라짐. 프로그램 수 증가 없음. 보통 단계 +2 ms 이내. |
| B | 물속 패스(픽셀 단위 안개·수면 분할). DOM 덮개 제거. | `shot-underwater`: 수면에 걸친 화면에서 수면 아래 벽돌이 흐려짐. 물막 안쪽 공기 공간이 공기로 보임(ts.png 장면). |
| C | 굴절, 거품, 코스틱(높음 단계). | 물 위 물체가 물에 번지지 않음(깊이 비교 테스트 장면). |
| D | 바다: `ocean.ts`/`.rs` + 패리티, 클립맵 수면, 해안 감쇠, `seaAt`. 섬 모드부터. | 파도 높이 CPU = 셰이더(샘플 점 비교). 헤엄·카메라가 파도를 따라 오르내림. |
| E | 심해: 해저 높이맵, 깊이대 조명, 암흑대. | 수심별 스크린샷 3장(10 m, 60 m, 200 m)에서 색·가시거리가 단계적으로 변함. |
| F | 유한한 물 마무리(샘 아이템, Rust, 교실 서버), 바다와의 흡수 규칙. | `fluid-volume` 패리티, 교실 E2E. |
| G | 안드로이드 WGSL 이식. | 같은 장면 스크린샷 비교. |

A·B가 지금 제보된 증상("물속인데 물밖처럼", "안쪽 경계가 보임")을 고치는 단계다.
D·E가 요청하신 곡선 파도와 심해다. F는 독립적이라 병행 가능하다.

## 8. 위험

- **성능**: 렌더 타깃 1장 + 전체 화면 패스 1회가 저사양 기기에 부담이다 → 단계 A에서
  실측하고, 예산을 넘으면 그 기기는 "낮음"에 남긴다. 추정치를 믿고 진행하지 않는다.
- **반투명 정렬**: 유리·구름 등 다른 반투명 물체는 2번 타깃에 없다. 물 뒤의 유리는
  굴절에 안 잡히고, 물 앞의 유리는 물 위에 그려야 한다 → 반투명 물체는 5번 직전에 따로
  그린다(지금 renderOrder 2/3 규칙의 일반화).
- **파도와 블록 세계의 이질감**: 곡선 파도가 레고풍 블록과 어울리는지는 취향 문제다 →
  단계 D 초반에 파고·파장 3가지 안을 스크린샷으로 비교해 정한다.
- **패리티 범위**: Gerstner는 sin/cos를 쓴다. TS(V8)와 Rust의 삼각함수는 마지막 비트가
  다를 수 있다 → 비트 일치가 아니라 허용 오차(1e-9 m) 패리티로 하고, 판정에 쓰는 값은
  양쪽에서 같은 방식으로 양자화한다. 지금까지의 "비트 일치" 원칙의 첫 예외라 명시한다.
- **범위**: A‒G 전체는 오늘 하루 작업의 몇 배다. 단계별로 끊어 배포하지 않으면 중간에
  라이브가 불안정해진다.

## 9. 결정이 필요한 것

1. **바다가 생기는 곳**: 섬 모드만인가, 교육 들판에도 있는가? (들판은 끝없는 평지라 바다를
   넣으려면 "해안이 어디인가"부터 정해야 한다.)
2. **심해에서 무엇을 하는가**: 구경·헤엄만인가, 건축도 되는가? 건축이 필요하면 §3.3의
   "해저는 블록이 아니다"를 바꿔야 하고 세계 높이·저장 한도 설계가 달라진다.
3. **지은 물의 규칙**: 유한한 물로 확정하는가? (§3.2와 단계 F의 전제.)
4. **파도의 성격**: 잔잔한 호수 같은 물결인가, 큰 너울인가. 탈것·낚시 같은 놀이 계획이
   있으면 파고의 상한이 거기서 정해진다.
5. **우선순위**: 지금 증상을 고치는 A·B를 먼저 하는가, 바다(D·E)를 먼저 하는가.
   권장은 A → B → D → E → C → F → G.
