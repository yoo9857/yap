# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CraftYap — a Roblox-style blocky 3D web game collection (English UI, crayon-doodle brand), one page whose start screen first asks **교육 모드 (education) / 게임 모드 (games)**: education goes straight into the endless field, games lists the four modes below. Live at **https://craftyap.com** (GitHub `yoo9857/yap`).

- **Daily Tower (tower)**: multiplayer obby. A new deterministic tower every day (KST midnight), client-authoritative movement with server sanity validation, persisted daily leaderboard.
- **Robo Builder (builder)**: idle game. Blocky workers construct real-scale voxel world landmarks (Eiffel 330 m, pyramid 230 m base…); no physics, no server dependency, localStorage save with offline settlement.
- **Craft Island (craft)**: single-player voxel sandbox (mine / craft / place). NO rapier — the voxel grid itself is the collider (`craft/voxelBody.ts` AABB sweeps, `voxelWorld.ts` DDA raycast). World regenerates from its seed; the save stores only the edit diff + inventory (zod-validated, hostile-safe). A blocky **pet** tags along (`craft/petCompanion.ts`) — dog, cat, elephant, giraffe or panda, swapped from the 🐾 **입양** chip under the machine-lab chip (or **Y**); **P** toggles sit/follow, and the choice is saved. The 🛋️ **가구** chip below it opens the furniture catalog (~50 pieces in 7 categories, colour variants, search — free and unlimited); **G** enters furniture mode without releasing the mouse (the hotbar becomes the category's furniture bar: **Q/E** category, **1‒9**/wheel piece, **X** colour, **R** turn, right-click place, hold left click to put away, **G** back to blocks). See `docs/FURNITURE.md`. On a PC it plays on pointer lock; phones and tablets get touch controls (see *Touch play*). Press **B** for the **machine lab** — a Besiege-style build-and-test-drive mode that *does* use rapier (see below).
- **Education field (field)**: Craft Island's sandbox (and machine lab) on an endless, empty flat field with 999 of every block that never run out (placing on a field spends nothing; `ensureFieldStacks` tops older saves back up). `craft/fieldWorld.ts` scrolls the usual 160×160 grid under the player in 16-cell steps (= 1 render chunk), banking edits by absolute coordinate, and sets `VoxelWorld.outsideColumn` so physics, rays and machines have ground beyond the grid; a big grass plane carries the view to the fog and the sky is fog-coloured so the far-plane cut never shows. Own save key, separate from the island. `O` cycles the render distance (fog is opaque exactly where chunks stop drawing; a gradient `skyDome.ts` makes the horizon the fog colour).
- **Classroom (education, live)**: the education lobby (`app/classLobby.ts`) offers 선생님 반 만들기 / 학생 반 참여하기 / 혼자 하기. A teacher opens a class under a **class name** (반 이름) + their own name; students type the class name + their own name, are shown **whose class it is** (`k-peek`) and confirm, then land in the same shared field. See *Classroom* below.
- **Learning themes (education)**: the education field is played as a THEME — the sandbox ("craft", the default) or the **fire drill** ("fire", 화재 체험). A teacher picks it in 반 만들기 (it belongs to the class from then on); 혼자 하기 asks too; solo deep link `?mode=field&theme=fire`. See *Fire drill* below.
- **Blast Royale (battle)**: arcade solo battle royale — you vs 7 bots (who also fight each other) on a random voxel island, hitscan blasters, 3-phase shrinking storm, last robot standing. Client-only (no server); reuses craft's world/physics/camera. Pure logic in `battle/{zone,combat,bots}.ts`; a 4 s weapons-free grace after the drop keeps spawns fair. The storm centre and the drop ring come from `battle/arena.ts` (the most open ground every spawn can walk to by 1-block steps) — never the castle, whose courtyard is walled in and battle cannot dig.

## Architecture

pnpm monorepo. `packages/shared` is consumed **as TypeScript source** (`"exports": "./src/index.ts"`) — no build step; Vite/tsx/vitest resolve it directly, and the production server bundles it via tsup `noExternal`. All packages are `noEmit` with `moduleResolution: bundler`. shared and server exclude the DOM lib so browser APIs there fail typecheck.

- `packages/shared` — zod wire protocol (single discriminated union on `t`, `PROTOCOL_VERSION` gate), deterministic level generator (`generateLevel(seed)` — identical output on client and server), daily-tower math (`daily.ts`: seed = f(date in KST), day boundaries), gameplay constants ported from the legacy prototype at 40 px/m (`constants.ts` — these define game feel, don't tweak casually).
- `apps/client/src/main.ts` — mode selector first; each mode lazy-loads. Rapier WASM (~2 MB) loads only for tower mode (craft/battle use the rapier-free voxel physics). `?mode=tower|builder|craft|battle|field` deep-links skip the selector (all E2E relies on this); `&reset=1` wipes a mode's localStorage save.
- `apps/server` — `ws` + pino. `Room` per ≤8 players on today's seed; `game/validation.ts` is the pure anti-cheat (unit-tested); `game/records.ts` persists daily bests in SQLite (better-sqlite3, falls back to in-memory if the native module is broken).

### Engine transition (`engine/`, full rules in `docs/ENGINE.md`)

A Rust engine grows BESIDE the TypeScript game (one core for web via WASM, the apps, PC and the server). It ships behind flags that are off by default. The TS module stays the reference until a part is switched; each Rust port is a line-for-line translation, and a parity test (`packages/shared/test/rust-parity.test.ts`) requires identical changes in identical order on randomized worlds. **Changing `fluid.ts`/`waterlog.ts` means changing `engine/crates/core/src/fluid.rs` too** (the engine workflow runs the parity test on those paths). Likewise **changing `craft/kitShell.ts` (the brick shell) means changing `engine/crates/core/src/kit.rs`** — `test/rust-kit.test.ts` requires the same float32s bit for bit, which is why the port carries three's earcut and V8's sort/hypot (a three.js upgrade that changes earcut fails that test). The same holds for **`VoxelView.scanChunk` ↔ `engine/crates/core/src/scan.rs`** (`test/rust-scan.test.ts` renders whole views both ways); the scan's tables come from the view (`makeScanner`), so a new block flag or face rule goes into both. Commands: `pnpm engine:build | engine:check | engine:test | engine:bench`. The world lives on the Rust side (no per-cell JS callbacks); persisted ids/formats never change in a port. **In the game:** `?engine=rust` builds the near brick shells on Rust (`VoxelView.useRustShells`, `kitRust.ts`) and runs solo water on Rust (`WaterSim` backends: `TsWaterBackend` reference / `RustWaterBackend` mirror). The mirror is fed by bulk `load` on start/scroll, `VoxelWorld.onWrite` per written cell (any NEW direct write into `cells/shapes/wet` must call it or reload), the field ring outside the window, and furniture by layout `version`. **On the server:** `FLUID_ENGINE=rust` runs class/party water on the Rust core. `ClassRoom` mirrors into it from the save restore, `writeEdit`, reset and furniture; furniture is compared by layout object AND version, because the layout is replaced on change. Any NEW mutation of `edits`/`wet` must go through `writeEdit` or be mirrored. Both sides fall back to TypeScript on a wasm trap. The one committed build is `packages/engine/wasm/` (`@robo/engine`: `/browser`, `/node`); the server's tsup copies the `.wasm` to `dist/engine-wasm/`, and the Dockerfile copies `packages/engine/package.json`. Rebuild with `pnpm engine:build` after any Rust change (CI `engine:check` fails on a stale build). Shape seals are the precomputed `SHAPE_SEALS` table; append to it when adding a shape code (a test recomputes it).

### Android app (`engine/crates/client`, `engine/platform/android`, full guide in `docs/ANDROID.md`)

The app is the NATIVE Rust client (wgpu on craftyap-core; no WebView; a GameActivity — only it has the IME for Korean typing — so keep games-activity at the version android-activity compiles against), package `com.craftyap.app` (debug `.debug`), audience includes children → Play Families policy, no ads. `pnpm app:android [release]` builds the .so for arm64/armv7/x86_64 with cargo-ndk, then Gradle (AGP 9.5, wrapper checksum pinned). The Android toolchain lives under ASCII paths in `C:\Android` (the user profile path is non-ASCII and breaks the NDK/Gradle/emulator). Load-bearing: the GPU device outlives the window (`Renderer::attach/detach` on resume/suspend, never a new device per resume); surface errors skip or reconfigure, a lost device rebuilds the renderer; every panic is logged (release is `panic = "abort"`); release signing only from `CRAFTYAP_UPLOAD_*` env vars. The wasm SOURCE_HASH excludes `crates/client`, `crates/net` and `platform/`. **Online is `engine/crates/net`** (the party/classroom protocol as serde types, a WebSocket link thread, the hub state machine): its types are checked against fixtures generated from the zod schemas, so **changing `packages/shared/src/protocol/{party,classroom}.ts` means running `pnpm engine:protocol` and updating `protocol.rs`** (CI `--check`; the round-trip test names the missing field). The app's water surface is the same `engine/crates/core/src/water_mesh.rs` the web uses (the only mesher). Likewise **changing the furniture catalog or `craft/furniture/model.ts` means `pnpm engine:furniture`** (the app's furniture is that code's own geometry, exported; CI `--check`), and the app's characters are the SAME `HOME.glb`/`TT.glb` (compiled in: a model change reaches both). The client's world is the web's: `world.rs` (generateIsland), `surface.rs` (createMaterialMaps) and `blocks_gen.rs` (GENERATED from blocks.ts — run `pnpm engine:catalog` after any catalog change; CI checks it) each have a parity test, so changing voxelWorld.ts generation, blockMaterials.ts or the catalog means changing the Rust too.

### Server cluster (`apps/server/src/cluster/`, full design + measurements in `docs/SCALING.md`)

`SHARDS=1` (default, dev) is the old single process (`single.ts`). Production runs `SHARDS=auto` (compose): `cluster/capacity.ts` decides from the container's cores/CPU quota/memory at boot — 1 core → single process, 2+ → a shard per core — so resizing the server needs no config change; compose deliberately sets no `cpus:` (a value above the host's cores stops docker from starting the container). `SHARDS=N|auto` runs a **primary** (HTTP, `/healthz`, `/metrics`, connection limits, the party hub) that hands each game socket — the raw TCP socket over IPC, after reading the upgrade — to one of N **shards** (classes, party fields, tower rooms). One process saturates at ~500 users; the primary relays no game traffic.

- **Every game socket names its game in the URL** (`?mode=class&room=…`, `?party=CODE`): that is its route (`directory.ts routeOf`). A new game socket type must put its key in the URL, or it cannot be routed.
- **The directory is sticky and load-aware, not a hash** (`LiveDirectory`): hashing spread class COUNT, not size, and left one shard at 100 % next to one at 22 %. Release is a compare-and-delete on a hand-off counter (`RouteLedger.seen` vs `handed`): never delete a mapping while a socket may be in flight, or a class opens on two shards with diverging fields.
- Shards guard ownership (`ClassManager.owns`, `ownsTower`) and answer a misrouted socket `bad-version` (it reloads routed) — never serve it.
- **Per-class state kept in a shard's memory must keep its route** (`ClassManager.holds`, which the shard's release sweep asks): a route given back lands on whichever shard is least loaded next time. The password-lock counter is in it for that reason — without it, waiting 5 s between guesses reset the lock.
- Party hub ↔ games is a mirror: roster pushed to shards on every seat change (`PartyManager.onRosterChange`), player counts reported back. `PartyGames.prepare` cannot fail in cluster mode.
- `/metrics` answers only direct loopback requests (anything with X-Real-IP/X-Forwarded-For is refused). `/healthz` is 503 until every shard is up; upgrades wait ≤5 s for a booting shard.
- `send()`'s boolean on IPC is backpressure, not failure — real failures arrive in the callback.

### Tower mode invariants (the anti-jitter contract)

Per-tick order in `app/game.ts` is load-bearing: input sample → moving platforms teleport (`setTranslation`, **not** `setNextKinematicTranslation`) → player KCC with explicit platform-delta carry → exactly one `world.step()` → triggers/NaN watchdog → interpolation commit. Everything rendered lerps from the same prev/curr pair (`physics/interpolation.ts`).

- **Do not switch moving platforms back to `setNextKinematicTranslation`**: it gives the body internal velocity that Rapier's KinematicCharacterController partially and unreliably applies to riders, double-carrying against our explicit delta (verified by tick traces; riders get flung).
- Moving-platform positions are analytic functions of the **shared server-time timeline** (`timelineSeconds`, slew-limited monotonic in `app/timeline.ts`) — never integrated incrementally, so all clients agree (~1 ms measured) and the server could recompute them.
- Sensors (checkpoints/hazards/goal) are analytic checks in `world/triggers.ts`, not physics events.
- Networking: client reports at 20 Hz; server validates displacement between **accepted** states against wall clock (lag bursts don't false-positive), respawn teleports are only accepted near the **anchor** (spawn/reached checkpoint — this is what blocks respawn-spam flight). Progress messages (`c-checkpoint`/`c-finish`) queue in `net/client.ts` and flush **after** the next `c-move` so the server always validates them against a position at the pad.
- Client `c-finish` carries a tick-precise time; server adopts it only within a tolerance window of its own wall-clock measurement.
- **Corrections go to the anchor while one is pending** (`correctionTarget`): after a death only positions near the anchor are accepted, so correcting to the pre-death `lastPos` failed every following move and kicked the player. A reconnect mid-run (`onWelcome(…, rejoin)`) restarts the run, since the new session's checkpoint is -1. Movement budget between accepted moves is capped at 4 s (silence never banks a teleport). The records DB is read before a player is registered (no ghost players), and `finished` is set only after `submitBest` succeeds.

### Builder mode (`apps/client/src/builder/`)

Pure logic (`state/sim/goals/save`) is DOM-free and unit-tested; the render layer reuses the tower's renderer/rig/sfx/effects. Key ideas:

- Landmarks are procedurally generated voxel blueprints at real-world scale with per-landmark voxel size (`landmarks.ts`); a bake pass adds AO/noise/weathering, `sealMicroGaps` fills pinholes. Blueprints are sorted bottom-up = build order. Keep each under ~80k blocks (test-enforced; ghost cap in `landmarkView.ts`).
- Economy is in **deliveries** (one worker trip = `deliverySize` voxels ≈ total/250), so pacing is constant regardless of detail. `settleOffline` must stay exactly consistent with live `tick` — there are unit tests and an E2E that assert equality to the gold.
- `landmarkView` batches instances by surface finish (masonry/metal/glass/emissive) and reveals them by count only; the "pour" runs at the economy's voxel rate (big catch-ups recap evenly over ~8 s).
- `cameraDirector.ts` guarantees the whole monument is always in frame (bounding-sphere fit distance recomputed per frame); shots are a shuffled deck, pinnable via `__roboBuilder.pinShot()` for screenshots.
- On landmark completion the **view** parades (finish pour + dwell on a pinned shot) while the sim already builds the next blueprint; HUD must describe the *view* landmark during the parade (`hud.update(state, view)`).

#### Builder VR (`vrDirector.ts` + `vrView.ts`) — the comfort contract

Builder is the only mode with WebXR (PC VR target). An "Enter VR" button appears automatically when `navigator.xr` reports an immersive-vr device, and only *after* `warmupGpu` (a shader compile inside a live session is a felt frame drop). `?vr=1` force-mounts the button for debugging. There is no controller input by design — it's an idle game, so head-look is the whole interaction.

In a session the **headset owns `camera.position/quaternion`**, so the viewer is placed by moving `GameRenderer.attachXrRig()`'s Group instead. `GameLoop` takes a swappable `FrameScheduler` because only `renderer.setAnimationLoop` frames carry a current head pose. VR lowers the flat grade's `near = 1.5 m` (it would clip the plaque and the blinder) but must **leave `far` alone** — the sky dome has a 1900 m radius, so a nearer far plane slices its back half off and the sky ends in a hard edge.

Four rules in `vrDirector.ts` are load-bearing and unit-tested. The flat-screen `CameraDirector`'s dollies and spirals are exactly what makes people sick, so VR gets its own director:

- The viewpoint **never moves while visible**; every change is a cut.
- Every cut is hidden behind a full-black blinder sphere parented to the camera (a visible teleport still reads as a lurch).
- **Yaw only.** Pitch/roll on the rig tilts the horizon against gravity; the viewer looks up with their own neck.
- A station's pose is **frozen on entry** — following the climbing build frontier would be slow vertical drift.

Because pitch is forbidden, a station's *height* is the only lever for what lands at eye level, and three non-obvious consequences shape the four stations (`plaza`, `yard`, `frontier`, `overlook`):

- **Elevated stations must stand well back.** The deck underfoot occludes everything steeper than ~58° below the horizon, and the build runs bottom-up, so a viewpoint near the build edge has all its placed blocks hidden beneath the deck with only unbuilt ghost left above. `frontier` therefore sits at *half* the build height and far enough out to keep the base above −55°.
- **There is no "above the summit" station** for the same reason: above the frontier is unbuilt ghost for most of a run.
- **Clearance comes from the blueprint, not `radiusM`.** `radiusProfile()` buckets the blueprint into height bands, because these landmarks run from a 96 m-wide ring 48 m tall (Colosseum) to a 331 m tower ending in a single 1.1 m voxel (Eiffel) — using the base radius at altitude parks you 130 m from a needle.

Mid-air stations get a railed platform, or height vertigo makes the view unwatchable; the deck is **set back** so the viewer stands at its front edge rather than over its middle, and the plaque sits down-and-left so it never covers the monument.

**The wrist shop panel** (`vrPanel.ts` + `render/vrInput.ts`) is the one part of VR that is input. Without it a headset gets a static-rate diorama — the idle loop *is* earn gold → hire crew → build faster, so a viewer who cannot spend watches the same rate forever. Layout and `hitTestPanel()` are pure and unit-tested, because a headless browser has no controller poses and that is the only way to know the buttons line up with what a ray hits (note `v` is bottom-up from the raycast, flipped into canvas space).

- Hand assignment comes from the runtime's `handedness`, never the controller index — a session that connects the right hand first would otherwise put the panel on the pointing hand.
- Handedness arrives *asynchronously*, so the panel starts mounted on the rig and moves to the wrist when a left hand appears. The always-on info plaque is hidden while the panel holds the rig slot (it shows the same numbers) and returns with the wrist mount.
- **Anything mounted on the rig lives or dies by its height.** At 0.42 m out and 0.68 m below eye level a panel sits 58° below the horizon — outside even a 100° fov, i.e. invisible and the shop unreachable. ~30° down, offset left of the monument's centreline, is the workable window.

One chunk's near form in one frame took up to 37 ms.
  - **Focus = the robot or the driven machine, never the camera**: the orbit camera swings metres when turned, which re-rang studs/LOD every frame.

#### Machine lab (`craft/machines/`) — build, test drive, missions

Craft's one rapier user: a connected blueprint becomes **one compound rigid body** in its own `World`, with the surrounding voxels baked into merged box colliders (3×3 chunks, refreshed as it moves). Full operating standard — units, approximations, exception table, what is deliberately NOT simulated — in `docs/MACHINE_PHYSICS.md`; keep it true when you change anything here.

- Layering is strict: `physicsRules.ts`/`aero.ts` (constants + pure force math) → `blueprint.ts` (parts, validation, stats) → `machinePhysics.ts` (rapier) → `workshop.ts` (3D + state) → `workshopUi.ts` (all DOM). `missions.ts` and `library.ts` are pure/storage-only and unit-tested without a browser; `library.ts` owns the saved slots (ids up to 48 chars, like names) and everything read back out goes through `validateBlueprint` first (`workshop.ts` keeps the working blueprint, mission record and assist flag).
- **Everything is a force at a mounting point** — thrusters, wings and balloons all call `addForceAtPoint`, which is why an off-centre nozzle spins the machine and a tail surface damps a spin. Nothing is special-cased per part name.
- Wings are **flat-plate normal force** (`F = -½ρAC·|v|·(v·n)·n`) evaluated with the *point* velocity `v + ω × r`, not the body velocity. No camber, no stall curve — an edge-on wing produces exactly zero, which is the behaviour the unit test pins.
- The **gyro only damps**, it never levels. So any residual thrust offset settles at a constant `torque / damping` spin rate; the presets are laid out mass-symmetric about the thrust line for that reason, and a redesign that ignores it will tip over on take-off.
- The test ground at (79.5, 18.5) is the island's only genuinely flat run (~48 m of level ground straight ahead). It was chosen by scanning the generated world — anywhere near the castle stops a build against a step within seconds, and a sloped spawn tips a wide machine onto a wingtip before the player touches a key.
- `PART_ORDER` must match the GLB: `machineVisual.ts` requires a mesh for every part kind, so a new part means editing `tools/generate-machine-assets.mjs` and re-running `pnpm assets:machines`.
- The build UI is keyboard-first (1‒8 parts, `R` rotate, `M` mirror, `X` erase, `F` frame, `Ctrl+Z`/`Ctrl+Y`) and the drive HUD is its own thing (`C` cycles chase/orbit/cockpit, `R` respawns without ending the run, Space/`Z` climb/descend — never Ctrl: Ctrl+W held with the throttle closes the tab and a page cannot cancel it). Steering wheels are those ahead of the cockpit; the spawn height is re-read from the 7×7 apron at every run. Chase camera follows **yaw only** — same reason as builder VR: following pitch and roll makes a flying build unwatchable, so the attitude ball carries that instead.
- Leaving the test bounds **respawns** rather than kicking the player back to the editor; only a non-finite state aborts the run.
- **Pilot assist is an autopilot, not physics** (`ASSIST` in `physicsRules.ts`, `G` to toggle, on by default). It drives the machine's *own* gyro torque and lift-thruster throttle and invents no force, so a build that cannot carry its weight still sinks and a build with no gyro cannot level itself. With assist off, `lift` takes the original raw path — the model this doc describes is exactly what you get. Keep that separation: tuning difficulty must never land in `PHYSICS_RULES`.
- The panel's **quick-play** buttons load an example *and start the test drive*, because the first thing a new player needs is to feel the thing move, not to learn a part palette.

### Classroom (`packages/shared/src/protocol/classroom.ts`, `apps/server/src/classroom/`, client `net/classClient.ts` + `craft/class{Sync,Hud}.ts`)

Live multiplayer for the education field, deliberately separate from the tower protocol (own `k-`/`s-k-` messages and `CLASS_PROTOCOL_VERSION`); it rides the same `/ws` endpoint, selected by `?mode=class`, so nginx/vite need nothing new.

- **Rooms are keyed by the CLASS NAME** (`classKey`, case/space-insensitive), not the teacher's name — two teachers with the same name can run differently named classes. A class name owned by another teacher (live or saved) is `room-taken`; the same teacher opening their live class twice is `teacher-taken`; a student name already online is `name-taken`; nobody may use the teacher's name as a student. `k-peek {room}` answers `s-k-room {exists, open, teacher}` and closes the socket — the student's confirm card. Protocol v5 (paced initial streaming and reliable replay; v4 added water).
  - **Classes saved before named classes** have no `roomName`: their key was the teacher's name, so that name IS their class name (`ClassRoom` defaults `roomName` to it). Re-open such a class with class name = teacher name.
- **A deploy never ends a class.** `ClassManager.shutdown()` saves and DROPS sockets; it must not call `room.close()` (that sends `s-k-closed`, which clients take as "lesson over" and never reconnect). The teacher's tab re-opens the class with its host key; students treat `no-class` on a reconnect as "wait for the teacher" for ~3 minutes.
- **One live tab per seat.** A seat taken over by its own key closes the old socket with reason `"replaced"`; `ClassClient` treats that close as terminal, or the two tabs would take the seat back from each other forever. The lobby cancels an in-flight connect when its step is left.
- **Liveness:** the welcome's optional `keepalive` (s) promises traffic at least that often (an empty `s-k-snap` when fewer than two players); a client that hears nothing for 5 periods closes and reconnects. Older servers send no `keepalive`, so no watchdog runs.
- **Server hardening:** rate-limit/malformed strikes decay (`STRIKE_DECAY_PER_S`, a flood still closes the socket, a long busy lesson never does); every socket message runs in try/catch (one bad message costs one socket, never the process); saved rows go through `readSaved` before becoming a `ClassRoom`; `k-peek` reads names via `ClassStore.meta` (`json_extract`), never the whole field; 5 wrong passwords lock a class (60 s, doubling to 15 min) except for its own host key; keys compare with `timingSafeEqual`; the student cap counts ONLINE students and the saved roster keeps 200 seats (oldest offline pruned); a refused edit returns the furniture layout to the sender only; a class whose save failed stays loaded until a save succeeds; taps are refused for 1.5 s after a >8 m position jump; chat drops control characters. `/ws` caps open sockets per client address (`MAX_CONN_PER_IP`, default 200 — a whole school shares one public IP) and in total (`MAX_CONNECTIONS`), trusting nginx's `X-Real-IP` only from a private peer; water-only changes save every 2 min, not 15 s.
- **Keys, not accounts.** The welcome hands out a key (teacher: host key, student: seat key) kept in localStorage per class. A refresh/reconnect re-takes the same seat; the teacher seat is only re-taken with its host key, so typing a teacher's name never grants teacher powers.
- **Everything on the wire is in ABSOLUTE field coordinates.** Each client scrolls its own voxel window, so grid coords differ per machine; `ClassSync` is the only place that converts.
- The server keeps the shared field as an edit diff vs the flat field (bedrock immutable, 300k-cell cap) and streams it to late joiners under a shared CPU budget and bounded transport queues; `ClassClient.connect()` resolves only once the whole field has arrived. Reliable updates received during loading replay after handlers are installed. Reconnect replaces the field and local identity, releases old remote avatars and moves embedded players out of restored terrain. See `docs/WORLD_RUNTIME.md` for invariants and repeatable resource checks.
- **Crowds (party fields hold 50) — netcode and rendering:**
  - Snapshots (`ClassRoom.snapshot`, 10 Hz) encode each player ONCE and join strings per recipient (`ClassPeer.sendSnap`), never echo a player to itself, send players beyond `SNAP_NEAR_M` (48 m) every `SNAP_FAR_EVERY`-th snapshot only, and leave default presentation fields out (positions to the cm). Measured at 50 players: 2.7 MB/s → 657 KB/s server out.
  - Every snapshot carries the server's clock `ts` (ms, `performance.now()`, not tick × 100 — timers drift). Without `ts` (older server) the old chase-the-latest lerp runs.
  - **`ClassSync.render` runs AFTER this frame's camera update** (and `scrollField` moves the camera with the window): it culls against the camera, and the previous frame's camera — still in the old window after a 16 m field scroll — hid a classmate right ahead for one frame each time a running player crossed a scroll (`tools/probe-remote-run.mjs` measures "hidden while in view").
  - `ClassSync.render` culls off-screen classmates against the camera frustum (character meshes have `frustumCulled = false`, so without this every classmate cost three passes from behind the camera), poses far ones every 3rd/6th frame, and keeps shadow + ink outline for the nearest `FULL_DETAIL` (10) only (`CharacterRig.setDetail` flips flags/layers, never materials). 40 players: 48 → 60 fps.

- **Friend taps** (`packages/shared/src/bonk.ts`, `k-bonk` / `s-k-bonk`): left click on a classmate gives a small shove. One `pickBonk` serves both sides with different strictness. ### Client rendering & assets

- **The player character is the HOME model, or TT** (`player/homeRig.ts`, CC0 Kenney derivatives under `public/models/characters/{HOME,TT}/` with face textures, visemes and frame-animated faces from `face-animations.json` drawn by `player/faceCanvas.ts`; see `docs/HOME_CHARACTER.md`). `CharacterRig` keeps one stable outer `root` and swaps the model inside it (`setCharacter`), so the camera, name label and position survive a switch: `main.ts` starts its download right after the mode is picked (it overlaps the class lobby — never cover the lobby with the boot overlay) and waits for the player's OWN model (the saved C-menu choice) before any mode builds a rig; the other model streams in behind play, and a rig that asked for it early shows the code-built mascot until it lands (`homeCharacterReady`); `CharacterRig` falls back to the code-built mascot if the asset fails. `/home-preview.html` is its animation review page (noindex).
- **Everything else is built from code, not modelled.** `player/blockParts.ts` is the shared toolkit — cached rounded boxes, one crayon-grain canvas, and an inverted-hull shader that gives every part the same 2 cm ink line. `player/rig.ts` is the biped cast (one cube body with a face decal, per-variant topper); `player/creatureRig.ts` is every quadruped pet. Both put feet at the origin and the face at +z, and expose `update(anim, speed, dt)` / `pop(impulse)`, so callers place them identically. Put new creatures through `blockParts` — a second grain canvas is a second GPU upload and the two casts drift apart in look.
- **`creatureRig.ts` is one skeleton, five species.** A chest-pivot spine, four legs in diagonal pairs, hinged head and tail, plus a per-species builder for the head, ears and extras (the elephant's trunk is a four-link chain; the giraffe's neck is its own raked group). Five separately-written gaits would drift apart the moment one was tuned. `SPECIES` is a three.js-free registry (collider, hop, pace, panel copy) that the physics, the save and the DOM all read — the adoption panel never imports a renderer.
  - **No outlines by default (owner's call, 2026-11-04 — the "clean, no black lines" look):** `GameRenderer` builds no ink pass and never shows `HULL_LAYER`; `?ink=1` brings the screen-space pass back, `?ink=hull` the hulls. Everything below describes those opt-in paths (and the review pages, which build their own `InkOutline`).
  - **The ink line is drawn in SCREEN SPACE** (`render/inkOutline.ts`), not per brick. Each part used to carry an inverted-hull shell, which rings every *brick* — so the head's shell cut a band across the neck, the tail's across the rump, and no line-weight tuning could remove them, because they were lines that should not exist. The pass renders characters (`INK_LAYER`) into a silhouette mask, finds the mask's edges, and inks those: one line per creature, none inside it, and a constant pixel weight at any distance. The hull shells still exist on `HULL_LAYER` as the WebXR fallback (a headset owns the framebuffer; render targets do not survive it) and `?ink=hull` shows them for comparison. Measured incremental cost: 51 draw calls and 40k triangles a frame.
    - **Ink only OUTSIDE the silhouette** (the composite's `best - c` test): inking both sides doubled the weight and turned paws and arms solid black.
    - Three traps, all hit: the mask needs **its own depth buffer** (re-rasterising the same triangles does not reproduce the scene's depth bit-for-bit, so `LESS_EQUAL` punches holes the edge detector faithfully inks — occlusion is a depth *comparison* in the composite instead); the composite must do its **own sRGB conversion** (a raw `ShaderMaterial` gets none of three's output chunks); and the extra passes must **freeze the shadow map**, which otherwise rebuilds per `render()` ignoring camera layers.
  - **That pass is what lets bodies be curved.** Torsos are chains of overlapping ellipsoids (`torso()`), with a deep chest, a tucked waist and a tapering rump — impossible while every extra brick added its own ring. Space the lumps at about a quarter of their depth: ripple is `R - sqrt(R² - (S/2)²)`, and the first attempt at nearly a full radius produced a caterpillar.
  - **The ink line scales with the part** for the fallback hulls (`outlineWidth` in `blockParts.ts`). A flat 2 cm is right for a 1 m body and ruinous for a 6 cm eye: the hull was wider than the brick inside it, so every face rendered as black blobs.
  - **Faces carry no ink line at all.** Eyes, noses and animal markings are spheres (`blob`). A rounded box at 5 cm still shows corners and a border, so an eye became a white tile, a nose a crate on the muzzle, and the panda's patches a pair of spectacle frames wider than its skull. The eye's dark rim is drawn as another sphere.
  - **Depth is the other half of a face.** Every layer must sit clearly in front of the last or the surfaces interleave into z-fighting stripes — and the eye must still stay ON the skull: pushed too far forward the panda's eyes floated off its silhouette in profile.
  - **`soft` is a fraction of the smallest dimension**, so the same value on two bricks of different depth gives two different corner radii, and a join that should be invisible shows as a groove. Matching a neighbour means computing the fraction, not copying it.
  - **Ground contact is derived, never configured.** `legs()` computes the leg length from `shoulderY` so the paw's underside lands on y = 0. When the two were independent numbers every pet hovered — the panda by 20 cm — and it survived a dozen screenshot reviews unnoticed. Unit-tested.
  - **Limbs need a shoulder.** A torso brick with four leg bricks bolted under it is a table: the join is a hard step ringed by two ink outlines. `legs()` adds a rounded hip/shoulder mass at each root overlapping both, and the limb reads as growing out of the body.
  - **Stride is in radians and is smaller than it looks.** Legs running shoulder-to-ground throw the foot much further per radian than stubs do; the pre-grounding values left every animal doing the splits.
  - Other rules worth keeping: a shape is **one brick or it is two things** (a point comes from a square turned 45° and half-buried, never a stacked taper); markings sit **on** a surface, never in front of it or inside it; anything animated over a rest pose must **add** to it, not overwrite it (writing `rotation.x` straightened the trunk every frame).
  - Judge every change with `tools/shot-pets.mjs`, which shoots a lineup, six body angles and **two face close-ups** per species. Reasoning about rounded boxes does not work and whole-body framing hides faces — the first cat was a rabbit, the first elephant wore solar panels, and the panda went through war paint, a scowl and a cardboard box.
- `apps/client/src/app/charPreview.ts` — `?preview=char` turntable (mascots behind, pets in front) with `__charPreview.pinDog(anim, yaw)` to freeze a pose for screenshots, the same idea as the builder's `pinShot()`.
- `render/textures.ts` — central texture registry (one cached instance per URL) + `warmupGpu` (upload every texture and `renderer.compile` every shader during the boot overlay). This is why mid-gameplay never pays a first-sight upload/compile hitch — route ALL texture loads through `loadTexture`, not `new TextureLoader()`.
- `ui/perf.ts` — `?perf=1` overlay (fps / worst-frame ms / draw calls / geo·tex·program counts / JS heap, and the worst frame's per-phase work: `perf.time("render", …)`); `__robo*.perf()` exposes the same sample for soak/leak checks.
- **Never let one material serve two shader variants per frame.** three re-derives the program (parameters + cache-key strings) on every switch — every object, every frame — which was the top of the CPU profile and ~90% of the garbage (GC pauses = the "turning stutters" reports). The rules that keep it from coming back:
  - **Every light is `layers.enableAll()`** wherever it is created. The ink mask camera only sees `INK_LAYER`s; a mask pass that saw no lights flipped the shared light state 2 → 0 → 2 each frame and invalidated EVERY lit material.
  - **Instanced shadow casters use `castsInstancedShadow(mesh)`** (`render/instancedDepth.ts`): three's single shared depth material otherwise flips between instanced and plain casters.
  - **A material is either instanced or not**: voxelView keeps twin materials (instanced near bricks / merged far chunks); instanced meshes go on `INK_INSTANCED_LAYER`, not `INK_LAYER`, for the mask pass's own override material. Mining shards are plain meshes, so they borrow the merged-mesh twins (`VoxelView.miningMaterials`).
  - **The same for skinned and double-sided**: skinned characters have their own ink layer and depth material (`INK_SKINNED_LAYER`, `castsSkinnedShadow`), and the fading robot materials are `forceSinglePass` (transparent + DoubleSide otherwise draws twice, flipping `side`).
- **Sound** (`audio/sfx.ts`, `audio/materialSounds.ts`):
  - **Recorded first, synth as fallback.** `public/audio/sfx/` holds 114 short mono MP3s cut from CC0 packs (sources in `CREDITS.txt`; keep it current when adding any). `manifest.json` lists the banks. They are fetched and decoded in the background after the first gesture, so they never delay boot, and until they arrive (or if they fail) every call plays its synth recipe.
  - **Blocks sound like their surface family** (`surfaceStyle(key).family`): `sfx.material("hit" | "break" | "place", family)`. Placing is a synth toy-brick snap on purpose, not a recording.
  - **Sound lands on what is drawn, never on its own timer** (`test/sound-sync.test.ts` pins this):
    - Clips are cut at their attack (`build_bank` envelope onset, re-measured at load by `clipOf`); `align: "peak"` schedules a clip so its loudest moment hits a given time. A whoosh is scheduled at its stroke's start to crest just before that stroke's blade impact (`PICKAXE.swing.impactAt`).
    - The pickaxe `strike` step arrives on EVERY tick of a swing: sound only when `pickaxeImpacts(from, to)` > 0, and the breaking blow plays the break alone.
    - Footsteps and hand-dig taps come from `CharacterRig.motionCue` in `CraftGame.cueSounds` (after `rig.update`): Walk/Run feet plant at gait phase 0 and 0.5, Crawl at ~0.44/~0.94, the Interact hand meets the block at 0.5 of its 0.7 s loop. Measured from the clips' foot/hand bones; re-measure if those clips change. The distance/beat fallbacks are only for the code-built mascot, which has no cue.
    - Friend taps: the tapper hears swing + bump at the Hit clip's contact (0.216 s) and the server echo is silent for them; everyone else hears it on the echo.
  - **Footsteps follow the block underfoot**: one on touch-down (the gait cue is muted for 160 ms after it, or a landing played twice), wet steps in shallow water, none swimming or seated; at a run the short legs plant ~8×/s, so steps get lighter and slightly higher with speed. Step levels sit at ~0.11–0.15 (players found the first pass too loud); a bank never repeats either of its last two picks.
  - **Soft ground (dirt, grass, sand, snow, wool) digs with the synth crunch**, not a footstep recording: the same sample for walking and digging read as one repeating noise. Breaking dirt/grass/sand uses the gravel crunch (never walked on); snow and wool break with the synth, since the snow bank is their footstep.
  - **The world is an acoustic space** (`audio/acoustics.ts`, pure and unit-tested; `Sfx` applies it):
    - Classmates' sounds go through an **HRTF `PannerNode`** (inverse distance from 2 m) placed against `AudioListener` (camera position + view yaw/pitch, set every frame), with air taking ~0.5 kHz of top per metre past 4 m.
    - **Our own block sounds are placed too** (`CraftGame.blockSound` → `Sfx.at(..., { own: true })`): heard from the block's direction, full level out to 5 m (the third-person camera distance), never occluded (the aimed block is in plain sight even when the camera is squeezed into a wall), and they keep the "into the bag" pop that classmates' breaks skip.
    - **Walls occlude**: `occlusion()` walks listener → source and sums each cell's damping (`CraftGame` supplies it: brick 1, solid furniture 0.6, glass/ice/leaves 0.35, water 0.15). Each wall costs ~6 dB and pulls a low-pass down (one wall ≈ 1.8 kHz). The source's own cell and ours never count.
    - **Rooms echo**: `measureRoom()` (14 short rays + a roof check, every 0.25 s) gives enclosure and size; `roomEcho()` turns that into a convolver send and tail. Impulses are cached per 0.25 s tail step and only swapped once the decay passes the step edge by 0.15 s (hysteresis): rebuilding one in a doorway every probe was a main-thread hitch. The send is NOT scaled by the effects volume (the sources already are). Open fields stay dry, and so does the machine lab (`labAudio`, which also leaves the water's muffle behind).
    - **Underwater** closes the master low-pass to 650 Hz (`setUnderwater`, from `updateUnderwater`).
    - `__roboCraft.audio()` reports the live state (echo, tail, master cutoff, banks, voices, `wallTo(x,y,z)`).
  - **Classmates are heard where they are** (`ClassSync.remoteSounds` → `hooks.sound` → `Sfx.at`): their steps and digs from their rig's own `motionCue`, pickaxe whoosh and blows from their relayed tool time, and their bricks from `s-k-edit` (`by` ≠ us and ≠ "" — the server's water — at most two per message, none for a stamp over 32 cells). `placeSound` sets the level (full within 2 m, silent by ~22 m) and the pan from the camera (`Sfx.setListener`, every frame). Their breaks skip our own "into the bag" pop.
  - **Every play varies** (random variant, never the same one twice running, ±7% pitch). All output goes through one compressor, with a 40-voice cap so a sand avalanche cannot become a wall of sound; classmates' sounds stop at 28, so a gathered class's footsteps never silence our own pickaxe. Noise layers slice one shared buffer; nothing is allocated per play. A failed manifest is retried by a gesture 20 s later; the underwater flag is remembered for a context created after it.
- **Light and colour pipeline** (every mode shares `GameRenderer`):
  - **Tone mapping is Khronos PBR Neutral, exposure 1.12**: near-identity for the painted palette (a slight lift of the mid-tones), it only rolls off highlights. The fill is a strong hemisphere light (1.5) with a neutral warm ground bounce, not grass green: green bounce turned the yellow mascot olive. The HOME/TT material carries a little self-light from its own texture (`emissiveIntensity` 0.18) so the shaded side keeps its true colour. The ink pass draws the world into a render target, where three skips tone mapping, so the composite in `inkOutline.ts` applies `#include <tonemapping_fragment>` itself. Custom sky shaders include `tonemapping_fragment` + `colorspace_fragment` so the canvas path (the default now, and XR) looks the same. Before this, normal play had no tone mapping at all and the fallback had ACES.
  - **Block materials use `vertexColors`** (the kit shells bake shading into a colour attribute). Every geometry drawn with them needs a `color` attribute (`whiteVertexColors()` in `voxelView.ts`); without one WebGL reads (0,0,0) and the studs and every far chunk drew black.
  - **Reflective blocks get a sky reflection map** (`render/skyEnvironment.ts`, one small PMREM per mode), attached to metal, gem, glass and ore materials by `VoxelView.setEnvironment` before the boot warm-up. Not `scene.environment`: matte blocks keep the light they were painted under. Its ground is neutral grey, not grass (gold reflecting green reads olive).
  - **Clearcoat below 0.1 is dropped** (`blockMaterials.ts`): invisible, but a second specular lobe on every pixel of every stone and wood block.
  - **The sun's shadow box snaps to whole shadow texels** (`GameRenderer.trackTarget`); a box sliding by fractions of a texel makes every shadow edge crawl while walking.
- **Draw between ticks** (`craft/smoothing.ts`): physics is fixed 60 Hz; the player and the pet are DRAWN `interpolate(prev, curr, alpha)` and the view angles `easeAngle` (~25 ms, absorbs a 125 Hz mouse vs a 144 Hz screen). Aim/mining use the exact angles. Unit-tested with irregular frame schedules — headless SwiftShader frame times are too noisy to judge smoothness by.
- **Reuse GPU resources, don't copy them**: one material per source when cloning (e.g. the robot fade clones per *material*, not per mesh), one cached geometry per shape, shared attributes for recoloured copies, one grain texture (`blockParts.crayonGrain`). Audit with `__roboCraft.scene()`: group materials/geometries/textures by content and look for copies.
- **The third-person camera rides OVER the floor** (`craft/craftCamera.ts`): a probe hit entered through a block's top face is floor and does not pull the camera in; the camera keeps its distance and is lifted `FLOOR_CLEAR` above the ground under it, and the robot fades by the camera's REAL distance from the head. Pulled in by the ground, looking up made the camera dive in and out with every jump — the own robot flickered (`tools/probe-self-blink.mjs`). Walls and ceilings still pull it in as before. Lift over the floor the probes HIT (a bridge or storey) or the column's ground, whichever is higher, then the line from the head to the camera must be clear (`los` raycast) — a floor hit ends a probe there, so a wall behind it (a room) is only caught by that check.
- **The robot's body is not glued to the camera** (`CraftGame.updateFacing`, `turnToward` in `smoothing.ts`): walking, it turns toward the camera-relative key direction (S walks it face-first toward the camera); mining/placing turn it back to the crosshair for `ACTION_FACE_TIME`; seated = seat yaw; first person = view. The classroom sends this body heading, not the camera yaw.
- Landing assets are size-capped: banner/paper are WebP, logo is a resized PNG; renderer caps `pixelRatio` at 1.5.

### Dev notes (`/note/`)

Public dev log. Posts are `notes/<slug>.md` (front matter: title/date/summary, optional tags/updated/draft — see `notes/README.md`). `tools/build-notes.mjs` renders them into `apps/client/public/note/` plus the sitemap's `notes:start…end` block; the output is **committed** like the machine GLB, so the server and nginx need nothing and IndexNow's changed-only mapping (`public<path>index.html`) sees each post. CI fails on stale output (`pnpm notes:check`). Pages reuse `guide/guide.css` + `guide.js` for header/footer, with `note/note.css` on top; asset links carry content hashes, so editing either stylesheet means re-running `pnpm notes`.

### Deployment

Runs on the same host as the `C:\poke` project, fully isolated (own port 8082, `/srv/craftyap`, separate SQLite). Deploy kit at repo root: `Dockerfile` (node:22-slim, only the server's 4 external deps — shared is bundled), `docker-compose.yml`, `ops/nginx/craftyap.com.conf` (+ bootstrap variant), `scripts/{deploy,backup-db}.sh`, and `.github/workflows/deploy.yml` (push to main → test → SSH deploy). Full runbook in `DEPLOY_KO.md`. Verify a running server with `node tools/smoke-prod.mjs <url>`. **Deploys are zero-downtime** (`scripts/zero-downtime-deploy.sh`, runbook in DEPLOY_KO.md): the new container starts beside the live one (compose projects `craftyap` :8082 ↔ `craftyap-green` :8083, one image `craftyap-app:latest`, one data dir), then for a few seconds `data/handoff.lock` makes every process refuse NEW game sockets 1013 (`net/handoff.ts`; stale after 60 s), nginx's upstream (`/etc/nginx/craftyap-upstream.conf`, included by the vhost as `craftyap_app`) is switched and reloaded, and the old container's SIGTERM saves every class and drops its sockets — players reconnect to the new one. The lock is what keeps a class from opening on the new container before the old one saved it; never remove it. Before stopping the old container the script proves a request THROUGH nginx reaches the new one (`/healthz` answers `x-instance: <hostname>`); every failure before that point removes the new container and restores nginx, so the old one never stopped serving. `tools/test-zero-downtime-deploy.sh` (CI) runs every path against stand-in docker/nginx — extend it with any change to the script. The live project is in `/srv/craftyap/active-project`, which the backup scripts read. **Every deploy snapshots the live DB before the hand-over** (from the still-running old container; `scripts/pre-deploy-backup.sh` → `/srv/craftyap/data/pre-deploy/`, newest 10, online backup — sqlite3 CLI or better-sqlite3 inside the running container, checked with `PRAGMA quick_check`) and aborts if it can't. Scripts that run inside the workflow's `ssh 'bash -se'` heredoc take `</dev/null`, or `docker compose exec -T` swallows the rest of the deploy script; that snapshot is the rollback point for saved classrooms. A change to the classroom save format must stay readable by BOTH the new and the previous server (rollback): add optional fields, never rename keys or rewrite rows.

### E2E harness conventions

Dev builds expose debug hooks per mode: `window.__robo` (tower), `__roboBuilder`, `__roboCraft` (give/mineAt/placeAt/craft/teleport), `__roboBattle` (killBot/damagePlayer/skipTime/snapshot). Two rules learned the hard way:

- Raw test teleports are **correctly rejected** by the server anti-cheat. Physics-only suites call `__robo.offline()` first; online movement must be kinematically plausible (`glideTo` micro-steps in e2e-multiplayer).
- Background tabs pause rAF (render + fixed loop), so cross-tab comparisons must read data updated by WS handlers, not mesh positions; bring a tab to front before reading its rendered state.

## Known limitations (see README for the user-facing list)

Mid-run reconnect resets server-side checkpoint progress; nickname = identity (no accounts); all rooms share the daily seed by design; sustained within-envelope speed passes validation (records still bounded by min-finish-time + checkpoint order).
